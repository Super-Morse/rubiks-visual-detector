Rubik's Visual Detector зсередини

Застосунок знімає кубик Рубіка камерою, розпізнає кольори стікерів нейромережею, перевіряє, що такий кубик може існувати, і показує розв'язок на 3D-моделі. Нижче крок за кроком розібрано, з яких частин він складається, які запити ходять між ними і який код виконується на кожному кроці.

Якщо часу мало, прочитайте «Карту системи» та «Життєвий цикл». Решта розділів докладно описує кожен крок, і їх зручно читати поруч із відкритим кодом.

Карта системи

У застосунку три учасники. Браузер показує інтерфейс і веде весь процес. Сервер на FastAPI на прохання браузера виконує дві операції. Модель — це файл нейромережі, який сервер запускає всередині себе. Є й четверта частина, солвер: програма на Go, скомпільована у WebAssembly. Браузер завантажує її із сервера, але працює вона вже в браузері.

  • камера та AR-рамка поверх відео
  • увесь прогрес сканування: крок, кадри, збережені грані
  • міні-сітка для ручного виправлення кольорів
  • 3D-кубик на Three.js і анімація ходів

Go-програма, яка за рядком із 54 літер знаходить ходи для збирання. Працює в браузері, без мережі.

Процесом керує браузер

Яка грань сканується зараз, які вже збережено, що показано на екрані: усе це змінні JavaScript в index.html. Сервер про це не знає.

Сервер нічого не пам'ятає

Кожен запит обробляється з нуля: прийшов кадр — повернулися кольори; прийшли 6 граней — повернувся рядок. Такий сервер називають stateless.

Розв'язок рахується в користувача

Сервер віддає лише рядок із 54 літер. Ходи для збирання знаходить солвер у браузері за мілісекунди.

Життєвий цикл одного збирання

Ось що відбувається від запуску сервера до анімації розв'язку. Кроки йдуть суворо по черзі; подробиці кожного кроку — у наступних розділах.

  1. Сервер стартує Сервер

    Команда uvicorn app.main:app створює застосунок FastAPI, підключає маршрути API і роздачу теки static/. Модель поки не завантажена.

  2. Користувач відкриває сторінку Браузер

    Браузер отримує index.html, підвантажує Three.js, wasm_exec.js і solver.wasm, вмикає камеру і запускає цикл розпізнавання.

  3. Сканування грані Браузер Сервер Модель

    Кожні 220 мс браузер надсилає кадр на /api/v1/scan-face і отримує 9 кольорів. Відповіді кількох кадрів об'єднуються голосуванням. Коли центр збігся з очікуваним кольором, грань заморожується для перевірки.

  4. Підтвердження грані Браузер

    Користувач за потреби виправляє кольори в міні-сітці й натискає Lock Face. Кроки 3 і 4 повторюються для всіх 6 граней.

  5. Перевірка розгортки Браузер Сервер

    Браузер зупиняє цикл сканування, вимикає камеру і надсилає всі 6 граней на /api/v1/validate-cube. Сервер перевіряє правила й повертає рядок Kociemba або помилку.

  6. Розв'язок і анімація Солвер Браузер

    Браузер передає рядок солверу, отримує список ходів і за кнопкою Solve Cube програє їх на 3D-кубику.

Уся сесія на одній діаграмі. Суцільні стрілки — запити й виклики, пунктирні — відповіді.

Як фронтенд спілкується з бекендом

Усе приходить з однієї адреси

Сторінку, статичні файли та API віддає той самий сервер FastAPI. Тому адреси в коді фронтенду відносні: fetch('/api/v1/scan-face') іде на той самий хост, з якого завантажено сторінку. Локально це localhost:8000, у продакшені — домен на Render. Спеціальний дозвіл браузера на запити до чужого домену (CORS) тут не потрібен, хоча сервер про всяк випадок дозволяє їх усім.

POST /api/v1/scan-face: кадр → 9 кольорів

1. Браузер готує кадр

Камера віддає відео 1280×720, якщо вміє. Функція extractSquareFrameBlob() вирізає з центру кадру квадрат за меншою стороною, малює його на невидимому canvas розміром 640×640 і стискає в JPEG з якістю 0,88. Розмір 640×640 обрано тому, що саме таке зображення приймає модель: серверу не доведеться його масштабувати.

static/index.html · extractSquareFrameBlob()
const minDim = Math.min(video.videoWidth, video.videoHeight);
const sx = (video.videoWidth - minDim) / 2;     // відступ зліва до квадрата
const sy = (video.videoHeight - minDim) / 2;    // відступ зверху
offCtx.drawImage(video, sx, sy, minDim, minDim, 0, 0, 640, 640);
return new Promise(resolve => offCanvas.toBlob(resolve, 'image/jpeg', 0.88));

AR-рамка на екрані лише підказує, куди піднести кубик. На сервер іде весь центральний квадрат, а зайві стікери сервер відсіює сам.

Файл надсилається як форма multipart/form-data, так само, як під час завантаження файлу через <input type="file">.

Параметр file: UploadFile означає «візьми з форми поле з іменем file». Ім'я параметра в Python має збігатися з іменем поля у FormData. Щоб розбирати форми, FastAPI потрібен пакет python-multipart, він є в requirements.txt. Параметр detector FastAPI заповнить сам через Depends, про це в розділі «Бекенд зсередини».

5. Ритм запитів

  • const scanTimer = setInterval(scanFrame, 220) викликає функцію кожні 220 мс. Ідентифікатор таймера зберігається, щоб потім зупинити цикл.
  • Прапорець isProcessing не дає надіслати новий кадр, доки не прийшла відповідь на попередній. Одночасно в дорозі не більше одного запиту: на швидкому сервері це близько 4 кадрів на секунду, на повільному рідше, але запити не накопичуються.
  • Поки грань заморожена (isFaceFrozenForReview), кадри не надсилаються: scanFrame() одразу виходить.
  • Коли всі грані збережено, finalizeCube() зупиняє цикл через clearInterval(scanTimer) і тоді ж вимикає камеру. Прапорець isScanCompleted на початку scanFrame() лишається як додатковий запобіжник.
  • Якщо камера ще не готова (video.videoWidth дорівнює 0), кадр пропускається.

POST /api/v1/validate-cube: 6 граней → рядок

1. Коли і що надсилається

Після Lock Face на шостій грані викликається finalizeCube(). Вона програє звук, ставить isScanCompleted = true, ховає нижню панель, зупиняє цикл сканування, вимикає камеру й надсилає всі збережені грані одним JSON.

clearInterval(scanTimer);                             // цикл сканування більше не потрібен
if (videoStream) {
  videoStream.getTracks().forEach(track => track.stop());   // вимикаємо камеру
}

const res = await fetch('/api/v1/validate-cube', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },

Якщо сервер не відповів зовсім, fetch викидає виняток, і браузер показує «Communication Error». З полів успішної відповіді фронтенд використовує is_valid і kociemba_string; detected_faces і message призначені для людей і Swagger.

Бекенд зсередини

Шари

Код сервера розкладено по шарах. Головне правило: шар domain нічого не імпортує з проєкту, а решта шарів залежать від нього. Так найважливіше, тобто поняття й правила кубика, не залежить від деталей на кшталт FastAPI, ONNX і OpenCV. Такий підхід називають чистою архітектурою.

Що відбувається під час запуску

uvicorn app.main:app імпортує app/main.py, і там по черзі:

  1. Settings()core/config.py

    Читає PROJECT_NAME і API_V1_STR зі змінних оточення або файлу .env. Якщо їх немає, бере значення за замовчуванням.

  2. FastAPI(...)main.py

    Створює застосунок. Схема API буде на /api/v1/openapi.json, Swagger — на /docs.

  3. add_middleware(CORSMiddleware, ...)main.py

    Дозволяє запити з будь-яких доменів.

  4. include_router(router, prefix="/api/v1")main.py

    Підключає ендпоінти: /scan-face з endpoints.py стає /api/v1/scan-face.

  5. @app.get("/health")main.py

    Проста перевірка, що сервер живий.

  6. app.mount("/", StaticFiles(directory="static", html=True))main.py

    Віддає файли зі static/, а на / — index.html.

Чому mount підключається останнім

Маршрути перевіряються в порядку додавання. Mount на / підходить під будь-який шлях, і якщо підключити його раніше за API, запити до /api/v1/... перехопить роздача файлів.

Модель на старті не завантажена

Вона завантажиться під час першого запиту до /scan-face. Шлях до неї в коді відносний, app/infrastructure/models/best.onnx, тому сервер треба запускати з кореня репозиторію. У Docker це забезпечує WORKDIR /app.

Впровадження залежностей

Ендпоінт не створює детектор сам, а оголошує, що детектор йому потрібен: detector: IFaceDetector = Depends(get_face_detector). Перед викликом ендпоінта FastAPI викликає get_face_detector() і передає результат у параметр. Усі такі функції зібрано в одному файлі:

app/api/deps.py
@lru_cache
def get_face_detector() -> IFaceDetector:
    return YoloOnnxFaceDetector()        # створюється один раз на процес

@lru_cache
def get_cube_validator() -> ICubeValidator:
    return StandardCubeValidator()

def get_cube_service() -> CubeScannerService:
    return CubeScannerService(validator=get_cube_validator())   # новий на кожен запит
  • @lru_cache запам'ятовує результат функції. У функції без аргументів результат один на весь час роботи процесу, тому детектор і валідатор — синглтони. Важка модель завантажується один раз.
  • get_cube_service() без кешу: сервіс створюється на кожен запит, але це дешево, всередині лише посилання на готовий валідатор.
  • Ендпоінт знає лише інтерфейс IFaceDetector. Тому в тестах реалізацію можна підмінити, і API перевіряється без нейромережі:
tests/unit/test_scan_api.py
app.dependency_overrides[get_face_detector] = lambda: mock_det   # мок замість ONNX

Шлях запиту /scan-face у коді

  1. scan_cube_face(file, detector)api/v1/endpoints.py

    Перевіряє, що content_type починається з image/, інакше відповідає 400. Читає байти: await file.read(). Викликає detector.detect(bytes). Перехоплює ValueError і перетворює на 422.

  2. YoloOnnxFaceDetector.detect()infrastructure/onnx_detector.py

    cv2.imdecode перетворює байти JPEG на масив пікселів у порядку каналів BGR. Якщо не вийшло, викидає ValueError.

  3. _preprocess()onnx_detector.py

    Робить letterbox: зменшує зображення зі збереженням пропорцій так, щоб довша сторона стала 640, і доповнює чорними полями до 640×640. Потім переводить BGR у RGB, значення 0–255 у 0–1 і порядок осей «висота, ширина, канали» в «канали, висота, ширина», додає вісь батча. Виходить тензор 1×3×640×640. Для кадрів із фронтенду масштаб дорівнює 1 і полів немає.

  4. session.run()onnxruntime

    Запускає модель на процесорі у 2 потоки. Сесія створюється один раз у конструкторі детектора.

  5. _postprocess()onnx_detector.py

    Для кожного з 8400 кандидатів обирає найімовірніший клас і відкидає кандидатів із впевненістю нижче 0,35. Потім NMS прибирає дублікати: з двох рамок, які перекриваються більш ніж на 35% за IoU, лишається впевненіша. Наприкінці координати переводяться назад у пікселі вихідного зображення.

  6. if len(boxes) < 9detect()

    Якщо стікерів менше дев'яти, повертається FaceScanResult(is_valid_face=False) із повідомленням «found N».

  7. _cluster_face_stickers()onnx_detector.py

    Якщо знайдено більше дев'яти (наприклад, у кадр потрапили стікери бічних граней), бере 9 стікерів, найближчих до медіанного центру, тобто до середини скупчення.

  8. _sort_into_3x3_grid()onnx_detector.py

    Сортує стікери по вертикалі, ділить на три ряди по три і сортує кожен ряд по горизонталі. Виходить порядок 0–8 зліва направо і згори донизу, індекс 4 — центр. За сильного нахилу кубика ряди можуть переплутатися, тому кубик краще тримати рівно.

  9. FaceScanResult → JSONFastAPI

    FastAPI перетворює Pydantic-модель на JSON за схемою з response_model.

Коли виправляти кольори

Поки грань не заморожена, кожен новий кадр перераховує currentStickers голосуванням і перезаписує ручне виправлення. Виправляти має сенс після заморожування, коли рамка зелена, а сканування на паузі.

3D-кубик

  • Кубик зібрано з 27 маленьких кубиків (cubie) розміром 0,95 з координатами від −1 до 1 по кожній осі; центрального не видно. У кожного шість матеріалів у порядку граней BoxGeometry: +X (R), −X (L), +Y (U), −Y (D), +Z (F), −Z (B). Зовнішні грані спершу сірі, внутрішні темні.
  • Таблиця faceletToCubieMap для кожного з 54 стікерів рядка Kociemba зберігає, який кубик і який його матеріал перефарбувати. За нею update3DFaceColors() розфарбовує модель просто під час сканування.
  • Під час переходу до наступного кроку зі STEPS беруться нові цільові кути. Цикл animate() кожен кадр наближає поворот кубика до цілі на 8%, тому кубик плавно повертається до грані, яку зараз сканують.
  • applyMove3D() анімує один хід: обирає 9 кубиків потрібного шару за координатою, прикріплює їх до тимчасового об'єкта-шарніра (pivot), повертає шарнір на 90° або 180° невеликими кроками, потім повертає кубики в загальну групу й округлює їхні координати й кути. Без округлення похибка дробових чисел накопичувалася б від ходу до ходу, і через кілька ходів шари перестали б знаходитися за координатами.

Рядок Kociemba і розгортка

Солверу потрібен опис кубика у стандартному вигляді: рядок із 54 літер. Кожна літера відповідає на питання «якого кольору стікер на цій позиції», але замість кольору пишеться літера грані, у якої центр такого кольору. Грані йдуть у порядку U, R, F, D, L, B, усередині грані — рядами зліва направо і згори донизу.

5Lпомаранчевийбілий36–44
6Bсинійбілий45–53

Підказки сканера точно повторюють орієнтацію граней на розгортці: над U лежить B із синім центром, над D — F із зеленим, над бічними гранями — U з білим. Детектор повертає стікери в тому порядку, в якому їх видно на знімку. Якщо тримати кубик інакше, порядок усередині грані зіб'ється. Кількість кольорів при цьому не зміниться, тому валідатор помилки не помітить, але рядок зазвичай описуватиме неможливий кубик, і солвер відмовиться його розв'язувати.

Як сервер будує рядок

app/domain/models.py · CubeState.to_kociemba_string(), спрощено
color_mapping = {
    face_state.center_color: face_pos          # white → U, red → R, ...
    for face_pos, face_state in self.faces.items()
}
for face_pos in [U, R, F, D, L, B]:
    for color in self.faces[face_pos].stickers:
        result.append(color_mapping[color].value)
return "".join(result)                         # 54 літери

Спершу за центрами будується словник «колір → літера». Білий центр стоїть на U, отже кожен білий стікер будь-де на кубику записується літерою U. Потім усі 54 стікери по черзі замінюються літерами. Приклад: якщо в лівому верхньому куті грані U (позиція 0) стоїть помаранчевий стікер, першою літерою рядка буде L, бо помаранчевий центр у грані L. Зібраний кубик дає рядок UUUUUUUUURRRRRRRRRFFFFFFFFFDDDDDDDDDLLLLLLLLLBBBBBBBBB.

Солвер у браузері

Солвер — окремий проєкт на Go (rubiks-solver), скомпільований у WebAssembly з налаштуваннями GOOS=js GOARCH=wasm. Результат — файл static/solver.wasm. Допоміжний wasm_exec.js з постачання Go додає в JavaScript клас Go, який уміє запускати такі модулі.

static/index.html · loadWasmSolver()
const go = new Go();                                 // клас із wasm_exec.js
const response = await fetch("solver.wasm");
const buffer = await response.arrayBuffer();
const result = await WebAssembly.instantiate(buffer, go.importObject);
go.run(result.instance);                             // Go-код реєструє window.kociembaSolve
  • Вхід: рядок Kociemba з 54 літер.
  • Вихід: рядок ходів, наприклад R L' U R F2 U R2 …. Літера — грань, яку треба повернути за годинниковою стрілкою, якщо дивитися прямо на неї; апостроф — проти годинникової; двійка — на 180°.
  • Перевірка: перед розв'язанням солвер перевіряє, що кубик фізично можна зібрати: немає перекрученого кута, перевернутого ребра й порушеної парності перестановок. Якщо перевірка не пройшла, повертається рядок, що починається з Error, і сторінка показує його в alert.
  • Швидкість: двофазний алгоритм Коцемби знаходить розв'язок завдовжки близько 20 ходів за мілісекунди.
  • Зібраний кубик: якщо рядок уже описує зібраний кубик, солвер не викликається, і сторінка одразу пише, що кубик зібраний.

Чому солвер не на сервері: обчислення швидке й не потребує нічого, крім рядка, який вже є в браузері. Окремий запит додав би затримку й навантаження на сервер.

Анімація розв'язку: кнопка Solve Cube запускає ланцюжок playNext(). Кожен хід програє applyMove3D(), а через 90 мс після його завершення починається наступний. Copy Solution копіює рядок розв'язку в буфер обміну.

Звідки взялася модель

Модель навчено заздалегідь, і вона лежить у репозиторії готовим файлом. Сервер її лише запускає. Навчання відбувалося так:

  1. Синтетичні даніtools/dataset-generator/index.html

    Генератор на Three.js у браузері малює кубик із випадковими кольорами, поворотом, світлом і фоном і сам обчислює рамки видимих стікерів. Розмічати вручну не потрібно. На виході ZIP у форматі YOLO, розбитий на навчальну й перевірну вибірки у пропорції 80/20.

  2. Справжні фото

    Синтетика не в усьому схожа на зображення з камери, тому до неї додаються розмічені справжні знімки. Цей підхід називають sim-to-real.

  3. Об'єднанняtools/merge_datasets.py

    Зводить назви класів різних датасетів до єдиного списку (6 кольорів і rubik_cube) і складає все в один датасет.

  4. Навчанняtools/train.py

    Бере попередньо навчену YOLO11n (nano, найменша версія), донавчає її 30 епох на зображеннях 640×640 і експортує в ONNX.

  5. У застосунокapp/infrastructure/models/best.onnx

    Файл близько 10,7 МБ зберігається просто в репозиторії. Серверу потрібен лише onnxruntime: PyTorch і ultralytics у продакшені не використовуються.

Перевір себе

Спробуйте відповісти, перш ніж розгортати відповідь.

Користувач відсканував три грані, і в цей момент сервер перезапустився. Чи втратиться прогрес?

Ні. Прогрес зберігається в змінних браузера, у capturedFaces. Сервер стану не зберігає. Кадри, надіслані під час перезапуску, просто не отримають відповіді, і цикл сканування продовжить роботу.

Що поверне /scan-face, якщо на кадрі знайдено 8 стікерів? Чому це не помилка?

Код 200 з is_valid_face: false і повідомленням «found 8». Для сканера це нормальна ситуація «грані поки не видно», а коди помилок залишено для справді неправильних запитів.

Коли модель завантажується в пам'ять і скільки разів?

Один раз, під час першого запиту до /scan-face. Функцію get_face_detector() позначено @lru_cache, і вона створює YoloOnnxFaceDetector лише під час першого виклику.

Як тести API працюють без нейромережі?

Ендпоінт отримує детектор через Depends(get_face_detector) і знає лише інтерфейс IFaceDetector. У тестах app.dependency_overrides підставляє замість нього мок.

Чим відрізняються дві відповіді 422 від /validate-cube?

Першу формує Pydantic, коли JSON не відповідає схемі: detail — список помилок. Другу формує ендпоінт, впіймавши CubeDomainError від валідатора: detail — рядок з описом порушеного правила.

Чому фронтенд надсилає квадрат 640×640, а не весь кадр 1280×720?

Модель приймає зображення 640×640. Квадрат такого розміру не треба масштабувати й доповнювати полями, і мережею йде менше даних.

Що станеться з циклом сканування після шостої грані?

finalizeCube() викликає clearInterval(scanTimer), і таймер більше не спрацьовує. Тоді ж зупиняються доріжки камери. Навіть якби таймер лишився, scanFrame() одразу виходила б через прапорець isScanCompleted, тож це прибирання, а не виправлення видимої помилки.

Валідатор пропустив кубик, у якого перекручено один кут. Що станеться далі?

Центри й кількість кольорів у порядку, тому сервер поверне 200 і рядок. Солвер у браузері перевірить, чи можна зібрати такий кубик, поверне рядок з Error, і сторінка покаже його в alert.

Навіщо applyMove3D округлює координати після кожного ходу?

Повороти рахуються в дробових числах, і похибка накопичується. Шар для наступного ходу обирається за координатою кубика, тому без округлення через кілька ходів кубики перестали б знаходитися.

Що зламається, якщо в main.py підключити app.mount("/", ...) раніше за include_router?

Роздача статики перехопить усі шляхи, включно з /api/v1/..., і API перестане відповідати.
